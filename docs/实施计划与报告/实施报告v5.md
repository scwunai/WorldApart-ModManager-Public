### 1.2 实现

`Plugin.cs` 的 `SettingsEntryHook` 重写为：

1. `OnShow` / `Start` postfix → `TryInject`。
2. `RemoveLegacyEntry(root)`：一次性递归找 `MODEntry` 并 `Destroy`（v4 内容区残留行），**v4 的 SystemPage 克隆逻辑整段删除**。
3. `FindDeep(root, "Frame#navSystem")` → `container = sys.parent`（`Frame#0`）；找不到则回落到 v4 的"Button 指向 VM"启发式。
4. 克隆 → 命名 `MODTab` → 子 TMP 文案改 `MOD 管理` → **`ForceRaycast`** 把克隆内全部 `Image.raycastTarget=true` → 加 `Button` 并接 `OnModTabClicked` → `btn.navigation.mode = None`。
5. `Maintain()`（由 `Update` 每 0.25 s 调用）：重设文案（防面板本地化改写）并把节点摆在 `navSystem` 正下方一格；有布局组时该写入会被布局覆盖，无布局组时它保证不重叠。

`navigation.mode = None` 是修第二类问题的：`EventSystem` 的键盘/手柄导航会把新 Button 当作可选元素，**Submit 事件会触发 `Button.onClick`**，表现为日志里 `MOD tab clicked t=32.08 mouseDown=False` 连打三条（鼠标没按）。**这解释了 v2/v3 时期的"无输入却反复 toggle"现象**：不是鼠标，是 EventSystem 的 Submit 导航。

同时入口语义从"toggle"改为**幂等打开**（`ShowPanel()`）：设置页 tab 负责打开管理面板，`TogglePanel()` 只留给 F10。这样即使仍有重复事件也不会把面板抖开又关。

## 2. Q2 视频替换路线验证

### 2.1 E-V1 —— 结论：路线要换，且已实证

**反汇编定序**（`VideoResourcePlayer.ResolveResourcePath`，RVA `0x1ABBCB0`）：

```
0x181abbd2b  call 0x180d4c750   ; AssetOverlay.TryResolveVideoOverride(location, out dir)   <-- 第一顺位
0x181abbd30  test al, al
0x181abbd32  jne  0x181abbde7   ; 命中即用它
0x181abbd70  call 0x1815fefc0   ; DlcContentManager.ResolveVideoBundle(location, out bundle)
0x181abbd86  call 0x181abb810   ; VideoResourceBuildPaths.GetBuildOutputDirectory()  <-- 内置
```

即 **Mod 覆盖 → DLC → 内置**。`NormalizeBundlePath`（RVA `0xD4C060`）= `Replace('\\','/').Trim('/')`，**不做大小写归一**。

**实测（`KIMI\v5_final_acceptance.log`）**：

```
[EXP] NormalizeBundlePath('cine/100000:1')  = 'cine/100000:1'
[EXP] NormalizeBundlePath('cine\100000:1')  = 'cine/100000:1'
[EXP] NormalizeBundlePath('Cine/100000:1')  = 'Cine/100000:1'          <- 大小写敏感
[EXP] TryResolveVideoOverride('cine/100000:1') BEFORE = False dir=<null>
[EXP] AFTER RegisterVideoOverride('cine/100000:1', '…\Mods\local.expvideo') = True
      dir=%USERPROFILE%\AppData\LocalLow\Nuverse\WorldApart\Mods\local.expvideo HasAnyOverride=True
[EXP] ResolveExternalRawFilePackage -> NotOwned pkg=<null>
```

三条结论：

1. **`Game.Mod.AssetOverlay` 是真正可用的 Mod 视频替换通道**：注册后 `TryResolveVideoOverride` 立即返回我的目录，而它就是 `ResolveResourcePath` 的第一顺位。这比"覆盖 mp4 字节"干净得多，也不依赖注入之外的任何东西。
2. **`SetExternalPackageResolvers` 不是 Mod 通道**：全工程唯一注册者是 `DlcContentManager.OnInit`（RVA `0x15FEA20`），本机无 DLC，所以实测恒 `NotOwned`。（此项与 M1 §⑥ 一致。）
3. **`ResourcePackage` 构造未做**：E-V1 的"外部包"分支需要 `new YooAsset.ResourcePackage(name)` + `InitializeAsync(InitializeParameters)` 自建一个包（YooAsset 2.3.9，OfflinePlayMode 下需自带 manifest 与根目录），工作量大且现在**已无必要**——AssetOverlay 路线已实证可用。按计划 §Q2.1"失败则记录证据并评估 E-V1b"，这里属于**路线被更好的方案取代**，不是失败。

**测试资产（已就绪，未做画面验证）**：`<M>\local.expvideo\` 下用 ffmpeg 生成了 6 秒 `testsrc2` 彩条测试片（549 KB，视觉上与游戏画面截然不同），并按三种可能的目录约定各放一份：`cine/100000/Video_cine_100000_bank_1.mp4`、`100000/Video_cine_100000_bank_1.mp4`、根下同名文件。目标 `cine/100000:1` 从 segments.json 的 `SourceIdentifier` 看是"拘魂殿使转阶段"演出。
**画面是否真的换掉未验证**：本模型无法触发该演出；override 已在本次交付的进程里注册着，委托方若走到该段演出应看到彩条测试片。**卸载方法**：不设 `MOD_EXP_VIDEO=1` 重启即可（override 不持久化）。

### 2.2 E-V2 —— 结论：**不校验，可原地覆盖 mp4**

**答案**：加载 raw 文件时**不做任何哈希校验，连长度都不比**，唯一的检查是 `File.Exists`。因此"直接覆盖 `<md5>.mp4`"这条**不依赖注入**的路线成立。

最强证据（二进制侧，全 `.text` 段 `E8 rel32` 扫描）：

- 全二进制里唯一会对文件内容算 CRC 的 `FileVerifyHelper.FileVerify`（RVA `0x6618650`）只有 **4 个调用者，全部在缓存文件系统**（`DCFSLoadAssetBundleOperation.InternalUpdate`、`DefaultCacheFileSystem.VerifyCacheFile`、`VerifyCacheFilesOperation.VerifyingCacheFile`、`VerifyTempFileOperation.VerifyInThread`）；`DefaultBuildinFileSystem` / `DBFS*` **一个都没有**。
- `FileCRC32Safely` / `FileMD5Safely` / `FileSHA1Safely` / `Game.HashUtility.FileSHA256` 的调用者数**均为 0** —— 这份二进制里没有任何代码会去哈希文件。
- 决策点 `DBFSLoadRawBundleOperation.InternalUpdate` @ `0x6600760`：`call File.Exists` → `test al,al; jne` 存在即 `Status=2 Succeed`，不存在则 `Status=3 Failed` + 字面量 `"Can not found buildin raw bundle file : "`（RVA `0x818B9C8`，与 YooAsset 源码文案逐字相同，反向印证函数身份）。`_bundle.FileSize` 只被写进进度字段，**无比较**。
- OfflinePlayMode 分支（`FsmInitializePackage.<InitRawFilePackage>d__5.MoveNext` @ `0x9DC810`）只 `AddParameter("APPEND_FILE_EXTENSION", true)`，**从不设 `FILE_VERIFY_LEVEL`**。
- `RawFileHandle.GetRawFilePath` 有 5 个调用者（都是 `LoadRawFileForVideoPlayer` 的回调），而 `GetRawFileData` / `GetRawFileText` 调用者为 **0** → mp4 是**按磁盘路径**直接交给播放器，连"读进内存再校验"的机会都没有。

源码侧一致（tag `2.3.9`，走 `ghfast.top` 镜像）：`FileVerify` 仅在 `verifyLevel == High` 时比 CRC32，而 `DefaultBuildinFileSystem` 的 `FileVerifyLevel`（ctor 里置 `Middle`）自己从不消费；`OfflinePlayModeParameters` 只有 buildin FS 一个字段，`DefaultCacheFileSystem` 根本不实例化。

实证旁证：1701/1701 条 `FileSize` 与磁盘一致；1701/1701 条 `FileCRC` 等于磁盘 CRC32 的**字节倒序**十六进制 —— 清单里的校验值是真值，本来比得出来，只是运行时从不比。

**一条必须注意的边界**：清单**本身**有校验。`ManifestTools.VerifyManifestData`（`0x661D780`）被 `LoadBuildinPackageManifestOperation.InternalUpdate` 调用，用 `RawFilePackage_1.0.hash` 校验 `.bytes`。**改 mp4 安全；改清单而不重算 `.hash` 会初始化失败。**

**未确定**（子代理自述）：静态推出而非动态观测（未动游戏进程）；未逐条反汇编那 5 个游戏侧消费方（但已排除它们自行哈希）；`AppendFileExtension` fallback 文件名的实际形态未实测。

全文：`KIMI\v5_q2_ev2.md`（35.9 KB）。

### 2.3 E-V3 —— 结论：**按 Bank 解析一次，缓存到该 Bundle 被卸载为止**

既不是"每次播放重读"，也不是"启动解析一次终身缓存"，而是**三级粒度**：

1. **Bundle 加载时现场扫盘发现 sidecar**：`VideoBundlePlayer.<CompleteBundleLoadAsync>d__69.MoveNext`（RVA `0x989ED0`）里 `Directory.GetFiles(dir, "*.segments.json")`（`0x98A146`）→ 去后缀（`0x98A1A9`）→ 逐 bank 调 `LoadVideoBankAsync`（`0x98A4C6`）。
2. **Bank 加载时无条件读**：`VideoBankPlayer.<LoadMergedVideoAsync>d__53.MoveNext`（RVA `0x98C270`）的 `File.ReadAllTextAsync`（`0x98C65B`）**之前没有任何 mtime/hash/缓存判断**。
3. **命中闸门**：`LoadVideoBankAsync`（RVA `0x9934C0`）先 `_bankLoads.TryGetValue(normalizedBankPath)`（`0x993596`），命中即 `jne` 直接复用、**不碰磁盘**；`UnloadVideoBank` / `UnloadBundleImmediate` / `UnloadAllBundlesImmediate` 会移除表项 → 下次重读。

缓存是**实例字段**（`VideoBundlePlayer._videoBankPlayers 0x38` / `_bankLoads 0x48`、`VideoBankPlayer._bank 0x50` / `_segmentNameToIndex 0x58`），**全镜像不存在 static VideoBank 缓存**。播放本身不再解析（`HasSegment` `0x992D30` / `FindPlayerBySegment` `0x991FA0` / `PlaySegment` 全走内存索引）；`LoadMergedVideoAsync` 全镜像只有 2 个调用点。

**对"追加帧"路线的含义**：同一已加载 bundle 上无法热生效，**但不需要重启进程** —— 关掉/重开空间视频面板（`SpaceVideoPanel.ReleaseVideoResources` `0x1A654D0` → `UnloadAllBundlesImmediate`）或重进 cine 会话（`CinematicPlayer.ApplyDesiredBundlesAsync` `0x13038F0` 等 6 处 `SetBundles` 做差集 `UnloadBundle`/`LoadBundle`）就会"卸载 → 重扫目录 → 重读 json"。

**一个削弱该路线的相邻发现**（子代理标注为"强静态证据、未运行时验证"）：cine 的 VPath 序列化在 AssetBundle 的 `CommonVideoClip.segmentVPath`（`0x18`）/ `CommonVideoClipBehaviour.segmentVPath`（`0x18`）上，**不从 segments.json 反推** —— 所以只改 json 不会让 Timeline 去播新 clip，还得同时处理 prefab 里的 segmentVPath。

**游戏目录改动：无。** 子代理只读打开了一个 segments.json 确认 schema。主模型**独立复核**：`MergedVideoResources~/cine/9907001/Video_cine_9907001_bank_1.mp4.segments.json` 的 SHA256 = `3fadf782…c3e47`（6391 B）与子代理报告一致，mtime 仍是 `Oct 5 14:08`（安装日期）；`find … -newermt "2026-10-06 13:00"` 在整棵 `MergedVideoResources~` 下**零命中**。

**未做**：三个运行时测试方案（A Harmony 计数、B 独占句柄挡读盘、C byte-exact 追加一条 segment）**均未执行**——本模型无法驱动视频播放。方案与备份/还原/SHA256 协议见 `KIMI\v5_q2_ev3_testplan.md`，委托方可在 1 分钟内跑完。

全文：`KIMI\v5_q2_ev3.md`（19.5 KB）。

## 6. 遗留风险

1. **Q1 视觉与点击未由本模型确认**（唯一硬缺口）。视觉风险低（同源克隆）；点击风险中（克隆节点可能仍被 UPF 组件拦截射线），若无效按 §1.4 的方案上一层透明 Image。
2. **`MODTab` 位置由 `Maintain()` 每 0.25 s 写入**：若该列由布局组驱动，会持续把节点标脏（开销极小但非零）；若布局组不存在，位置完全依赖这个补偿。更干净的做法是确认列上到底有没有布局组件——这正是我用 `GameObject.GetComponents(Type)` 想枚举组件类型时**导致 coreclr 访问违例**（`0xc0000005`）的地方，已回退并在代码注释里留痕。
3. **`AssetOverlay` 视频 override 目前仍注册着**（`cine/100000:1` → 测试目录）。委托方若走到"拘魂殿使转阶段"会看到彩条测试片；不设 `MOD_EXP_VIDEO=1` 重启即恢复。
4. **E-V1 的 `ResourcePackage` 自建未探索**：AssetOverlay 路线已够用，但若将来需要"整包替换"（不只是视频），仍需研究 `new ResourcePackage(name)` + `InitializeAsync` 的最小可用参数组合。
