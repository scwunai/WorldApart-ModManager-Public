## 0. 结论摘要

| 验收项 | 结果 |
|---|---|
| **标志 B**：插件自检 `marker present = True` | **达成**（`KIMI\v3_acceptance_log.log`） |
| **双向可逆** | **达成**：`basecfg_patch` OFF → `marker=False`；ON → `marker=True`（同一进程内，无需重启） |
| 标志 A（游戏内截图） | 未由本模型确认，需委托方在游戏内看一眼（见 §5.3） |
| 根因问题「`ApplyChanges()` 为何返回 0 条」 | **已定位，且不止一个原因**（§2） |

**根因一句话**：`ModTablePatch.EnumerateIn(unitRootDir)` 会在传入的 unit root 后面**再拼一层 `tables`**（`<unitRoot>\tables\*.patch.json`），而三个 Mod 包的 `mod.json` 把 `root` 写成了 `"tables"`，于是游戏去找 `<包>\tables\tables\`——目录不存在时该方法**静默返回空表**（`failure` 仍是 null），补丁从未被读入。修好布局后又暴露出第二个缺陷：`storytest` 的两个 unit 共用同一个补丁目录，导致 unit 级开关互相顶替；以及第三个流程缺陷：只要存在任何"非热表"变更，原生 `ApplyChanges()` 会**跳过**热表重建，而这一步本应由被隐藏的工坊 UI 触发的"重进"来完成。

## 2. 根因结论

### 2.1 缺陷 A：`EnumerateIn` 自己会再拼一层 `tables`，而 `mod.json` 的 `root` 已经指到了 `tables`

反汇编 `ModTablePatch.EnumerateIn`（`GameAssembly.dll` RVA `0xD7EE50`，日志化反汇编见 `KIMI\tools\il2dis.py`）：

```
0x180d7eee4  lea rcx, [rip + 0x74a48fe]    ; rva 0x8223788  (元数据用途槽)
...
0x180d7ef23  test rbx, rbx                  ; rbx = unitRootDir
0x180d7ef26  jne 0x180d7ef39
0x180d7ef28  ...                            ; 参数为 null 时取默认根
0x180d7ef39
0x180d7ef50  mov rdx, [rip + 0x74cdeb1]     ; 槽 RVA 0x824CE08
0x180d7ef57  mov rcx, rbx
0x180d7ef5a  call 0x18546e3e0               ; Path.Combine
0x180d7ef6c  call 0x18544ba50               ; Directory.Exists
0x180d7ef71  test al, al
0x180d7ef73  je  0x180d7f0cb                ; 不存在 -> 直接返回空表
0x180d7ef86  call 0x18544c020               ; Directory.GetFiles(dir, pattern)
```

两个字符串常量的值从 `KIMI\il2cpp_out\script.json` 的 `ScriptString` 段按键 `Address` 反查得到：

```
      "Address": 136629768,      <- RVA 0x824CE08
      "Value": "tables"
      "Address": 135724800,      <- RVA 0x816FF00
      "Value": "*.patch.json"
```

即等价于：

```csharp
var dir = Path.Combine(unitRootDir, "tables");
if (!Directory.Exists(dir)) return new List<ModTablePatch>();   // 0x180d7f0cb: mov rax,rdi; ret —— 不写 failure
var files = Directory.GetFiles(dir, "*.patch.json");
```

而 `ModUnit.RootDir` 的由来：`mod.json` 里 `"root": "tables"`，加载时 `Path.Combine(packageRoot, root)` = `<包>\tables`。于是实际查找路径是 `<包>\tables\tables\*.patch.json` —— 不存在，**静默返回空表**。

**运行期证据**（`KIMI\v3_probe_run1.log`，修复前）：

```
PROBE: IsHot(tbnpcbasecfg)=True IsHot(tbnpcaipersona)=True IsHot(tbmainmenubutton)=False
PROBE-ENUM[unitRoot(menu_patch)] C:\...\Mods\com.kimi.modmanager\tables -> 0 patch(es) failure=<null>
PROBE-ENUM[unitRoot(persona_patch)] C:\...\Mods\com.kimi.storytest\tables -> 0 patch(es) failure=<null>
PROBE-ENUM[unitRoot(basecfg_patch)] C:\...\Mods\com.kimi.storytest\tables -> 0 patch(es) failure=<null>
```

注意 `failure=<null>` —— 这就是为什么此前所有排查都看不到任何错误：**该方法在目录缺失时不报错、不抛异常、不留 failure，只是返回一个空 List**。而 `ModRegistry.HasEnabledPatch()` 是纯注册表判断，与磁盘无关，所以一直是 `True`，把排查方向带偏了。

一个附带发现：`ModUnit.RootDir` 不能等于包根目录。`ModPackage.TryResolveInsideRoot`（RVA `0xD79B40`）在 `StartsWith(root + 分隔符)` 上做包含检查，`"."` 经 `Path.GetFullPath` 归一化后等于根目录，不带尾分隔符，会被判为"不在根内"而拒绝。所以 unit root 必须是包的**严格子目录**。

### 2.2 缺陷 B：同一个补丁目录被两个 unit 共用 → unit 级开关互相顶替

修好缺陷 A 后，`ApplyChanges()` 返回 1 条、`marker present = True`，但**关掉 `basecfg_patch` 后标记仍在**（`KIMI\v3_rev_run1.log`）：

```
REV: step1 (basecfg_patch OFF)  marker=True tablesBuiltWithMods=True
   toggled com.kimi.storytest|basecfg_patch|0 -> False (IsEntryEnabled now=False, ...)
```

`IsEntryEnabled now=False` 说明注册表侧确实关掉了，但表里补丁还在。

原因是 `EnumerateIn` 的粒度是**目录**，不是 unit：

```
PROBE-ENUM[unitRoot(persona_patch)] ...\com.kimi.storytest\content -> 2 patch(es)
PROBE-ENUM[unitRoot(persona_patch)]    table='tbnpcaipersona' ... upsert=1
PROBE-ENUM[unitRoot(persona_patch)]    table='tbnpcbasecfg'  ... upsert=1
PROBE-ENUM[unitRoot(basecfg_patch)] ...\com.kimi.storytest\content -> 2 patch(es)
```

两个 unit 的 `root` 都是 `content`，各自都返回**两份**补丁。所以关掉 `basecfg_patch` 后，仍处于启用态的 `persona_patch` 会把 `tbnpcbasecfg.patch.json` 一起读进来。

### 2.3 缺陷 C：存在"非热表"变更时，原生 `ApplyChanges()` 会跳过热表重建

反汇编 `ModBootstrap.ApplyChanges`（RVA `0xD710E0`）：

```
0x180d711a0  call ModRegistry.Rescan                       ; ApplyChanges 自己先 Rescan
0x180d711bc  call ModConfigOverlay.Rebuild                 ; 收集启用中的补丁
0x180d71214  mov rax, [rax + 0xb8]                         ; Singleton<ModRegistry>.lazyInstance.Value
0x180d7123f  call 0x180658140                              ; ModRegistry.Instance
0x180d71261  call ModTableTiers.ReenterOnly(rbx, 0)        ; <- 返回值就是 ApplyChanges 的返回 List<string>
0x180d7126c  je  0x180d712fb                               ; null -> 抛异常
0x180d71272  cmp dword ptr [rax + 0x18], 0                 ; List<T>._size == 0 ?
0x180d71276  jne 0x180d712d2                               ; 非空 -> 跳过重建
0x180d712a3  call ConfigManager.RebuildTablesWithMods      ; 只有空的时候才重建
0x180d712e9  call ModOverlayCoordinator.Sync
0x180d712ee  mov rax, rbx                                  ; return list
```

即：**`ApplyChanges()` 的返回值不是"应用了几条"，而是"哪些表需要重进才生效"**。只要这个列表非空，热表（`tbnpcbasecfg` 属于 Hot）也不会被重建——原生设计是让调用方（工坊 UI）先做一次重进，重进时 `OnGameLoaded()` 才去 `RebuildTablesWithMods()`。

本作 `tbmainmenubutton`（`com.kimi.modmanager` 的主菜单按钮补丁）不是 Hot 表（`ModTableTiers.IsHot(tbmainmenubutton)=False`），只要它启用着，这个列表就永远非空，热重建就永远被跳过。而工坊 UI 被隐藏，没有任何东西会去执行那次重进——**补丁因此永远不落地**。

### 2.4 被证伪的假设（计划 §1.2 / E-B 里的候选）

| 假设 | 证据 | 结论 |
|---|---|---|
| pending-set（只应用"新 diff"） | `ModConfigOverlay.Rebuild` 每次重建 `s_byTable`；且把**全部** unit 关掉后 `overlay.HasAny=False`（§5.2 step3） | 不成立 |
| 需要先 `OnGameLoaded` | `[HOOK]` 证明游戏自己就调了，调了也没用 | 不成立 |
| 存档内嵌 ModStamp / ModIdMap | 见 §4 E-C：`gameworld.msgpack` 里搜不到任何 `ModStamp`/`ModIdMap`/`Mod` 字段 | 不成立 |
| 表实例错配（UI 读另一份表） | 修复布局后自检直接读到补丁文本，且该实例就是 `ConfigManager.Instance.Tables` | 不成立 |
| `ConfigManager.tableBytes` 缓存 | 清掉 241 条缓存后行为不变 | 不是主因（仍保留清理，见 §3.4） |

## 3. 修复实现

### 3.1 修 mod 包布局（缺陷 A）

不改任何补丁文件内容，只把它们挪到游戏真正会去读的位置，并同步 `mod.json` 的 `root`：

```
修复前                                   修复后
<包>/mod.json  root="tables"             <包>/mod.json  root="content"
<包>/tables/xxx.patch.json               <包>/content/tables/xxx.patch.json
   -> 游戏查 <包>/tables/tables/ (无)       -> 游戏查 <包>/content/tables/ (有)
```

原文件已完整备份到 `KIMI\Mods_backup_pre_v3\`。`KIMI\mod_template\` 同步修正，避免下次部署再踩同一个坑。

### 3.2 一个 unit 一个补丁目录（缺陷 B）

`com.kimi.storytest` 拆成两个 unit 目录：

```
com.kimi.storytest/persona/tables/tbnpcaipersona.patch.json   (root="persona")
com.kimi.storytest/basecfg/tables/tbnpcbasecfg.patch.json     (root="basecfg")
```

这样 `EnumerateIn` 每个 unit 只返回自己的补丁，unit 级开关才真正有意义。

### 3.3 插件补上"重进"这一步（缺陷 C）

新增静态类 `ModSync`（`KIMI\bepinex_plugin\Plugin.cs`，约 40 行），每次改动 mod 状态后按下面的顺序执行：

```csharp
var applied = ModBootstrap.ApplyChanges();          // 返回值 = 需要重进的表
if (applied.Count > 0)                              // 非空 = 原生代码把热重建跳过了
{
    InvalidateTableCache();                         // ConfigManager.tableBytes.Clear()
    ModBootstrap.OnGameLoaded();                    // 其内部会跑 ConfigManager.RebuildTablesWithMods()
    ForceReloadTables();                            // ConfigManager.ForceReloadTables(受影响的表)
    ModBootstrap.ApplyChanges();
}
```

`ModSync.Apply(tag)` 被 `[HarmonyPostfix] ModBootstrap.OnGameLoaded`、启动扫描、F10 开关、以及每 10 秒的自检轮次统一调用，并用 `_inApply` 重入保护避免 `OnGameLoaded → postfix → Apply → OnGameLoaded` 递归。

关键点：`ConfigManager.ForceReloadTables(IEnumerable<string>)` 是**公开**的（BepInEx 的 interop 里齐全，只是 `RebuildTablesWithMods` 之类不在），它绕过了 `ReloadTables(incremental)` 的"源文件未变就跳过"逻辑，使关闭补丁能立刻回退。

### 3.4 其它

- `InvalidateTableCache()`：清 `ConfigManager.tableBytes` / `tableFileWriteTicks`。实测单独清它不足以回退（主因是缺陷 B），但它是重载路径上的正确卫生动作，保留。
- 探针代码（`DeepProbe` / `ProbeEnum`）保留在插件里，作为可复现的诊断入口，只跑一次，不产生每帧开销。
- 可逆性自测默认关闭，设 `KIMI_REV_TEST=1` 才在启动后第 4 轮自检时自动跑一遍；F10 窗口里也有 "Reversibility test (off -> on)" 按钮。

### E-B 反汇编三问的答案

**问 1：`ApplyChanges` 遍历的数据源是什么？**
`ApplyChanges` 本身**不遍历补丁**。它依次调用：`ModRegistry.Instance.Rescan()` → `ModConfigOverlay.Rebuild(null)` → `ModTableTiers.ReenterOnly(ModRegistry.Instance, 0)` → 条件性 `ConfigManager.Instance.RebuildTablesWithMods(false)` → `ModOverlayCoordinator.Sync(null)`。
真正的数据源在 `ModConfigOverlay.Rebuild` 里：

```
0x180d72c64  mov rcx, [rip + 0x74c32dd]
0x180d72c6b  call 0x183fbb040            ; Singleton<ModRegistry>.Instance
0x180d72c84  call 0x180d7b670            ; ModRegistry.ActiveUnits(ModUnitType.TablePatch)   (edx=2)
0x180d72d3c  call 0x180d7ee50            ; ModTablePatch.EnumerateIn(unit.RootDir, out failure)
0x180d72de6  call 0x1822d2e00            ; 按 table 归并进 Dictionary<string, List<ModTablePatch>>
```

即：**启用的 TablePatch unit → 各自的 RootDir → `EnumerateIn` 扫出的补丁文件**。`s_byTable` 每次 `Rebuild` 重建（不是累加）。

**问 2：什么条件下条目被跳过 / 集合为空？**
三层：
1. `ModRegistry.ActiveUnits(TablePatch)` 为空（没有启用的 table_patch unit）→ 循环体一次都不走。
2. **`EnumerateIn` 在 `<unitRoot>\tables` 不存在时返回空 List 且不设置 failure**（`0x180d7f0cb: mov rax, rdi; ret`，rdi 是刚分配的空 List）→ 这是本次的核心。
3. `ApplyChanges` 里 `ReenterOnly(...)` 返回非空时跳过 `RebuildTablesWithMods`（§2.3）。

**问 3：`OnGameLoaded` 是否向那个数据源填东西？**
是。`OnGameLoaded`（RVA `0xD71310`）在首次调用时做 `LocalModSource.EnsureRoot()` / `ModMigration.MigrateLegacyGeneratedPacks()` / `ModRegistry.LoadPrefs()` / `ModRegistry.Rescan()`（由 `[rax+0x48]` 一次性标志守护），随后无条件调用 `ConfigManager.RebuildTablesWithMods`（`0x1814e8fe`），最后跳转 `ModOverlayCoordinator.OnGameLoaded`。
而 `RebuildTablesWithMods` 内部是 `ModConfigOverlay.Rebuild()` → `ModConfigOverlay.HasAny` → `ReloadTables`，所以**它确实会把补丁铺到表上**——前提是补丁能被 `EnumerateIn` 扫到。

## 7. 遗留风险与建议

1. **标志 A 待委托方确认**（需截图）。
2. **`Mods` 布局属于"隐式约定"，没有文档也没有校验**。`EnumerateIn` 在目录缺失时静默返回空表是整个排查最大的时间黑洞。建议：
   - 短期：以 `KIMI\mod_template\` 为准，新 Mod 一律 `<包>\<任意子目录>\tables\*.patch.json`，且 **一个 unit 一个子目录**；
   - 中期：插件已加 `DeepProbe`，F10 一键就能看出"每个 unit 扫到几个补丁"，加 Mod 后先点一次即可自查。
3. **`ForceReloadTables` 的表名目前是硬编码的**（`tbnpcbasecfg` / `tbnpcaipersona` / `tbmainmenubutton`）。换 Mod 或加新表时要同步维护。更稳的做法是在 `ModConfigOverlay` 重建后取 `PatchedTableNames`——当前 interop 暴露的是 `IEnumerable<string>` 接口代理（不是 `List`），需要走 `TryCast`/手动枚举，故先按硬编码处理，已记在 `Plugin.cs` 注释里。
4. **`tbmainmenubutton` 是 Reenter 级表**，它的补丁（主菜单"KIMI MOD 管理入口"按钮）在热重建路径下能否真正出现，取决于主菜单是否重建 UI；本报告只验证了 `tbNpcBaseCfg`/`tbNpcAiPersona` 两张 Hot 表。若委托方发现主菜单按钮没出现，属预期内的另一件事，需要单独为重进路径做处理。
5. **gpShell 风险不变**：v2 报告 §E6 记录的三条禁区（改其 IAT、`LdrRegisterDllNotification`、VerifierDlls）依然有效，本次未触碰。
6. **BepInEx 版本**：be.788（v2 已替换）。若游戏更新导致元数据版本再次超出 LibCpp2IL 支持范围，取最新 be 构建即可。
7. **`KIMI\Mods_backup_pre_v3\` 建议保留**，直到委托方确认游戏内表现无误。
