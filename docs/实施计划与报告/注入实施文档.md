## 3. 已验证事实（实测，按路线组织）

### 3.1 静态代理 DLL 注入【废弃】
WorldApart.exe 与 UnityPlayer.dll 的导入表只有 gpShell.dll。游戏目录放 winhttp.dll/version.dll 作静态代理：gpShell 会加载它（模块列表里可见 `<G>\WINHTTP.dll`），但**时机早于 UnityPlayer**，doorstop 判定"非 Unity 进程"而保持惰性 —— 这就是早期"代理在却无任何 BepInEx 输出"的原因。两个代理文件已移走（`.doorstop` 后缀存档）。

### 3.2 IFEO VerifierDlls 路线【废弃】
- 机制本身有效：填不存在的 DLL → 游戏无法启动；填系统 winhttp.dll → 游戏正常运行；填 doorstop winhttp.dll → 弹 0xc0000142。
- **VerifierDll 的 DllMain 收到的 reason 是 4（DLL_PROCESS_VERIFIER），不是 DLL_PROCESS_ATTACH** —— 这是 v1-v4 全部"无反应"的根因。
- v5 处理了 reason=4 并能在 Verifier 阶段写标记文件、建线程，但 **CreateThread 出现在 Verifier 阶段会杀死宿主进程**（notepad 与游戏都因此起不来；用户已确认 notepad v4/v5 都报错属此现象）。该路线彻底放弃，不要再试 notepad/VerifierDll 组合。
- Verifier 阶段 CRT stdio 未初始化、%TEMP% 不可靠 —— 若将来必须在此阶段做诊断，用纯 Win32 API + exe 所在目录。

### 3.3 IFEO Debugger + 启动器路线（当前主线，链路已大半打通）
- IFEO 按 **exe 文件名**匹配；硬链接新名不触发（已对 notepad 与游戏双向验证）。
- "启动器 CreateProcess 返回 err=87" 曾经被认为是递归保护/CSRS 标记，**实际是乌龙**：把进程访问权限位（PROCESS_VM_WRITE=0x20）当成了 dwCreationFlags 传入。CreateProcess 的 creationFlags 用 0，之后再 OpenProcess 拿注入权限即可。
- 已不存在的误会一并澄清：不存在"IFEO 标记沿子进程继承"的问题，helper 中转是为防御递归保护加的保险，现在**保留它**（无害且防 Windows 行为差异）。
- Unity 数据目录按 exe 名推导：硬链接名必须有对应 `<名>_Data`，用**目录联接**解决（实测弹窗确认此规则，联接后游戏正常启动）。
- 游戏进程结构：启动器创建的壳进程（gpShell，无 UnityPlayer）会自行派生**子进程**才是真正的 Unity 进程（宿主含 UnityPlayer.dll）。用 Toolhelp32 轮询 `WorldApart*` 中含 `UnityPlayer.dll` 的进程即可可靠定位（已实现于 wastart 的 FindUnityProcess）。
- 每次测试前必须杀光旧进程，否则轮询会命中上一轮的残留 Unity 进程（踩过）。

### 3.4 Mod 系统逆向结论（后续阶段直接用）
- `Game.Mod` 命名空间。`ModRegistry : Singleton<ModRegistry>`：`EnsureInitialized()`、`Rescan()`、`LoadPrefs()`/`SavePrefs()`、`IsEntryEnabled()`、`SetEntryEnabled(modId,unitId,npcId,bool)`、`Packages`、`ActiveUnits`。`ModBootstrap.ApplyChanges()` 应用补丁。
- 注册表 `HKCU\Software\Nuverse\WorldApart`：`MOD_ENABLED_ENTRIES_V2_h2913630511`（REG_BINARY，UTF-8+NUL，多行 `modId|unitId|0`）；键名 `_h` 后缀 = PlayerPrefs 的 DJB2a。
- 补丁格式 `tables\<表名>.patch.json`：`{"keyFields":["npcId"],"upsert":[...],"remove":[]}`，camelCase。
- 三个测试 Mod 已在 `%USERPROFILE%\AppData\LocalLow\Nuverse\WorldApart\Mods\`（`com.kimi.storytest` 等），注册表启用项已写好，管线一唤醒即应生效。

## 4. 当前卡点（本次工作的起点）

### 4.1 现象
链路已跑到最后一步：wastart helper 成功创建 `WorldApart_kimi.exe`、轮询到 Unity 子进程、`OpenProcess`/`VirtualAllocEx`/`WriteProcessMemory` 全部成功、`CreateRemoteThread(LoadLibraryW, "<G>\kimi_probe.dll")` 返回成功句柄 —— **之后远程线程永远不结束**（`WaitForSingleObject(20s)` 超时后本应打 FAIL/OK 日志，实际 40 秒+ 后日志仍停在 `INJECT: remote thread created, waiting`，探针标记文件 `kimi_probe.txt` 始终未出现）。

### 4.2 解读
远程线程卡在 `LoadLibraryW` 内部，两种主假设：
- **H1（进程级阻断）**：gpShell 对 `LdrLoadDll` 做了 hook/过滤，外来 DLL 的加载被无限期阻塞或死锁。
- **H2（加载器锁死锁）**：注入时刻主线程正长时间持有加载器锁（Unity 启动期大量 DLL 加载），远程线程等锁等到天荒地老。20s 超时后 helper 会写 FAIL 日志 —— 但日志没有出现，说明连 `WaitForSingleObject` 的返回路径都没走到（或者 helper 进程已死/被挂起，**先用 `Get-Process wastart` 确认 helper 是否还活着**，这是第一个待办）。
- **H3（注入目标时机不对）**：gpShell 的检测只在启动窗口期严格，主菜单后放松 —— 需要对比"启动早期注入"与"进主菜单后注入"。
- **H4（远程线程本身被劫持/不调度）**：某些反篡改会拦截外来线程。用无操作入口点（如 `GetTickCount`）做远程线程对照可判别：若对照线程也永不返回，则问题在线程机制而非 LoadLibrary。

### 4.3 现有诊断工具
- **探针 DLL**（`KIMI\injector\probe.c`）：DllMain 向 `<G>\kimi_probe.txt` 写"加载成功/失败+GetLastError"，并在进程内自加载 doorstop 以获得真实错误码。当前 wastart 注入的就是它（`wastart.c` 中 `kimi_probe.dll`，成功后可改回 `kimi_door.dll`）。
- wastart 日志：`<G>\KIMI\injector\kimi_inject.log`（UTF-16LE）。
- 模块/进程诊断脚本：见 2.1。

## 5. 实施步骤（按优先序）

### E0. 现场确认与基线（必做）
1. 杀进程（2.2 节命令）。
2. 按 2.1 核对现场文件齐全（尤其硬链接、Data 联接、IFEO Debugger 值、`kimi_probe.dll`）。
3. 重跑一次基线复现卡点：`powershell -ExecutionPolicy Bypass -File <G>\KIMI\launch_watch3.ps1`，等 60s 后检查三处日志（inject/probe/BepInEx），并 `Get-Process wastart` 确认 helper 死活。把结果原样写进报告。

### E1. helper 死活与超时路径
- 若 helper 已退出但无 FAIL/OK 行：说明它死在 `WaitForSingleObject` 之后的路径（不可能）或进程被外部干掉（查事件日志/WER，`Get-WinEvent Application`）。
- 若 helper 挂着：`WaitForSingleObject` 行为异常，改用手动轮询 `WaitForSingleObject(th, 0)` + `GetExitCodeThread`（STILL_ACTIVE=259 判活），每 2s 记一次日志，看清线程是死了还是活着。

### E2. 无操作远程线程对照（判别 H4）
把注入入口从目标进程外的 `LoadLibraryW` 换成 `GetTickCount`（kernel32 导出，立即返回），远程线程不带参数。若对照也永不返回 → 线程机制被 gpShell 干预（转 E5 手工映射路线）；若对照正常返回 → 问题专指 LoadLibrary（H1/H2），做 E3。

### E3. 注入时机扫描（判别 H2/H3）
给 wastart 加环境变量/参数控制注入时机：UnityPlayer 出现后分别延迟 0s/5s/20s/60s 再注入；另测一次"等到 `GameAssembly.dll` 模块出现后再注入"。哪种时机下探针标记出现，就用哪种。

### E4. 注入目标对照
分别注入 壳进程（无 UnityPlayer）与 Unity 子进程，对比结果。早期在壳进程远程加载 game-dir winhttp 曾**快速返回 NULL**（不是挂死）——若壳进程现在能加载探针而 Unity 进程挂死，说明阻断发生在 Unity 初始化后期（il2cpp 区域），对定位 hook 位置很有价值。

### E5. 手工映射注入（若 H1 成立的标准解法）
LoadLibrary 被 hook 时的业界标准绕行：**手动映射**——`VirtualAllocEx` 申请内存、写入 DLL 文件内容、在目标内远程执行一个 stub（或本地计算）完成重定位与导入解析（只依赖目标已加载的 kernel32/ntdll 基址），直接调用 DllMain(DLL_PROCESS_ATTACH)。先用手工映射加载**探针**验证可行性，再映射 `kimi_door.dll`。注意 doorstop 代理的 DllMain 需要其导入表解析（kernel32 等）+ 它注册的 DLL 通知回调要正常工作。工作量中等，实施模型若 2 小时内无法在 E1-E4 取得突破，直接转本路线。

### E6.（备用）分析 gpShell 的加载路径干预
静态/动态分析 gpShell.dll 对 ntdll 加载函数的 hook（`LdrLoadDll`/`LdrRegisterDllNotification` IAT 或内联 hook 检测）。仅在 E5 也失败时做，报告里记录发现即可，不追求完美。

### E7. 打通后：BepInEx interop 与插件（规格已定，照做即可）
1. 探针换回原目标：wastart.c 的 `kimi_probe.dll` 改回 `kimi_door.dll`，重编译部署，重启游戏。
2. 等 `BepInEx\interop\` 生成（**可能 5–20 分钟，游戏像卡死，禁止杀进程**，提前告知用户）。
3. 建插件项目 `<G>\KIMI\bepinex_plugin\`（net6.0 类库，`dotnet build -c Release`），HintPath 引用 `<G>\BepInEx\core\BepInEx.Core.dll`、`BepInEx.Unity.IL2CPP.dll`、`Il2CppInterop.Runtime.dll`、interop 生成后的 `<G>\BepInEx\interop\GameAssembly.dll` 及 UnityEngine 程序集（以 interop 目录实际文件为准）。
4. 插件规格：
   - `[BepInPlugin("com.kimi.modmanager","KIMI Mod Manager","1.0.0")]`，`Load()` 里 `AddComponent<ManagerBehaviour>()`；
   - `Update()`：`Time.time>5` 且未执行时调 `Game.Mod.ModRegistry.Instance.EnsureInitialized()` + `Rescan()` + `Game.Mod.ModBootstrap.ApplyChanges()`；
   - `OnGUI()`：F10 开关的 IMGUI 窗口（标题"KIMI Mod Manager"），遍历 `ModRegistry.Instance.Packages`，checkbox 调 `SetEntryEnabled(modId,unitId,npcId,...)` + `ApplyChanges()`；
   - 类型一律来自 interop GameAssembly.dll 的 `Game.Mod` 命名空间；`Singleton<T>.Instance` 的确切成员名以生成 API 为准。
5. 产出拷到 `<G>\BepInEx\plugins\`，重启验证：苏倾盏档案页出现【KIMI·MOD生效】标记 + F10 窗口可开关三个 Mod。

## 8. 环境坑（全部踩过）
1. Git Bash 会吞 PowerShell 的 `$` 变量 → PS 逻辑写 `.ps1` 文件再 `-File` 执行；`.ps1` 必须 UTF-8 带 BOM。
2. GitHub 直连超时 → 下载走 `https://ghfast.top/https://github.com/...`。
3. `taskkill //F //IM python.exe` 误杀面太大；杀游戏用 `Get-Process WorldApart*,wastart | Stop-Process -Force`。
4. IFEO 注册表删除后立即重建会遇"标记为删除"→ 重试或先 sleep（setup_ifeo_debugger.ps1 已内置重试）。
5. `wastart` 日志是 UTF-16LE，bash 下用 `iconv -f UTF-16LE -t UTF-8` 读；探针日志是 UTF-8。
6. cl.exe 编译带 DllMain 的 DLL 不要加 `/NOENTRY`；wsprintfW 在 user32.lib，Verifier 阶段慎用 user32。
7. Windows SDK 版本只有 10.0.22621.0 / 10.0.26100.0 可用，build.bat 已配好。
8. 游戏双进程结构：壳（gpShell）+ 子（Unity）。判断"真身"看模块列表有没有 UnityPlayer.dll。
9. 硬链接 exe 需要配套 `<名>_Data` 联接，否则 Unity 弹 Data folder not found。
10. 测试循环：`杀进程 → rm 三处日志 → launch_watch3.ps1 → 等够时间 → 读日志`，时间要给足（helper 轮询最多 60s + 注入等待 20s）。
