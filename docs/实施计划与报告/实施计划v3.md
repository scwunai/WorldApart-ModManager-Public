## 3. 实施步骤

### 步骤 0 —— 部署现有改动并跑协议 P1（半天内必须完成，大概率直接出答案）
1. 杀进程：`Get-Process WorldApart*,wastart -EA SilentlyContinue | Stop-Process -Force`，sleep 2 后再确认一次（Steam 可能拉起重开）。
2. 拷贝 `KIMI\bepinex_plugin\bin\Release\KimiModManager.dll` → `BepInEx\plugins\`（若报文件占用 = 进程没杀净，回到 1）。
3. 清日志：`rm BepInEx\LogOutput.log, KIMI\injector\kimi_inject.log`。
4. 启动：`powershell -ExecutionPolicy Bypass -File KIMI\launch_watch3.ps1`（15 秒观察窗），随后游戏保持运行。
5. **协议 P1（需要用户配合，报告里记录每一环的时间线）**：
   - 进存档到游戏世界；
   - 观察 `LogOutput.log` 是否出现 `[HOOK] ModBootstrap.OnGameLoaded fired`。出现 = 游戏自己确实在加载存档时调用了它（此前从未证实）；**没出现** 本身就是一个重要结论（说明本作可能不走 ModBootstrap.OnGameLoaded，补丁应用挂在别处）。
   - 按 F10，点 **"Force OnGameLoaded() + Apply"** 按钮，记录点击后 30 秒内日志中的 `forced OnGameLoaded: ApplyChanges -> N item(s)` 与随后自检的 `marker present`。
   - 若标记出现 → 直接进第 5 节收尾；若仍 0 条 → 进入步骤 1 排查。

### 步骤 1 —— "0 条"根因排查（按序做，每步都要日志证据）

**E-A. 制造"待定变更"对照实验**
猜想：`ApplyChanges` 只应用"上次应用后新产生 diff 的条目"（pending set）。`SetEntryEnabled` 可能负责往 pending set 写条目。
实验：在插件里加一段一次性实验代码（或 F10 按钮"Toggle-off-on + Apply"）：对 `com.kimi.storytest|basecfg_patch|0` 依次 `SetEntryEnabled(false)` → `SetEntryEnabled(true)` → `ApplyChanges()`，记录每步返回值。若返回条数变 >0 → 机制清楚，把"默认启用"流程改成"先全禁再按注册表启用"或"启用后再 Apply"；若仍 0 → E-B。

**E-B. `OnGameLoaded` 原生实现逆向**
`ApplyChanges`/`OnGameLoaded` 只有 native 代码。对 `GameAssembly.dll` 反汇编两个函数（RVA 见 `KIMI\il2cpp_out\dump.cs` 中 ModBootstrap 一节：`ApplyChanges` Offset 0xD703B0 附近、`OnGameLoaded` 同区段）。工具建议：委托方环境有 Python，`pip install capstone`（若装不上，用 MSVC 的 `dumpbin /DISASM /RANGE`）。**目标不是全读，是回答三个问题**：
   1. `ApplyChanges` 循环遍历的数据源是什么（某个 static List/Dictionary？字段名可从 `dump.cs` 的 ModBootstrap 私有字段对照）；
   2. 什么条件下条目被跳过/集合为空（找 `cmp ...; je` 早退分支）；
   3. `OnGameLoaded` 是否向那个数据源填东西（若是，P1 的 Force 按钮本应起效；若它读的是存档里的 ModStamp……结合 v2 报告"新档无 ModStamp"线索，**本作可能要求存档内嵌 Mod 清单，补丁只对"带 ModStamp 的存档"应用**）。
报告里给出关键反汇编片段与结论，不要贴大段原始反汇编。

**E-C. 注册表与存档侧核查**
- 枚举 `HKCU\Software\Nuverse\WorldApart` 全部键值，找 `ModIdMap`/ID 分配映射类键；`ModIdAllocator.Export()` 的数据是否该持久化在某处。
- 用 msgpack 解析当前存档 `gameworld.msgpack`（此前已验证可解析）：搜 `mod`/`ModStamp`/`ModIdMap` 字段。结论写进报告（存在/不存在/字段样例）。

**E-D. 直接改表对照实验（决定性）**
绕过 Mod 管线验证"表实例对不对"：插件里用 Harmony 或在 F10 按钮中**直接改** `ConfigManager.Instance.Tables.TbNpcBaseCfg` 里 id=100000 的 `propPlot`（interop 属性可 set 则 set，不行就反射/指针写）。然后：
   - 若自检立刻 `marker present = True` 且**游戏内档案页也变了** → 表实例就是 UI 读的这份，问题 100% 在 Mod 管线的"应用"环节，回 E-A/E-B 继续；
   - 若自检 True 但档案页不变 → 档案页读另一份数据（快照/存档内副本），按 E-E。
注意：改完把值改回原文，避免污染后续实验。

**E-E.（仅在 E-D 指向"另一份实例"时做）**
追踪 UI 档案页数据源：从 `dump.cs` 找社交/档案页相关类（关键词：Archive、Profile、Social、NpcRelation），看它们读 `ConfigManager.Tables` 还是 `GameWorld`/`SaveData` 里的副本；用 Harmony postfix 打日志确认运行时实际来源。然后在正确实例上重复 E-D 的直接修改验证。

### 步骤 2 —— 修复实现
根据步骤 1 的根因，在插件中实现对应的应用策略（可能形态，按根因选）：
- pending-set 型：调整启用/应用顺序；
- OnGameLoaded 依赖型：Force 按钮逻辑自动化（检测到进世界后自动调用一次）；
- 存档 ModStamp 型：**评估**是否值得做存档注入（改动存档文件有风险，报告中给出风险与方案，**未经委托方确认不要实施**）；
- 表实例错配型：在正确实例上直接套补丁数据（保留原生 Mod 管线的启用/禁用语义，只是改"写入目标"）。
