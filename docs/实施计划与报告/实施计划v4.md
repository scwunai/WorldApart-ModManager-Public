## 0. 现状关键事实（侦察已完成，直接采信）

### 0.1 插件（`KIMI\bepinex_plugin\Plugin.cs`，681 行）

- `Plugin`：`PluginGuid="com.kimi.modmanager"`、`PluginName="KIMI Mod Manager"`；Harmony id `"com.kimi.modmanager.hooks"`；程序集 `KimiModManager.dll`。
- `ManagerBehaviour.Update()`：
  - F10 切换 `_show`；**`_show` 默认 `true`**（IMGUI 窗口默认开）。
  - 开局 5s 做初始扫描（EnsureInitialized/LoadPrefs/Rescan/EnableEverythingByDefault/ModSync.Apply/SavePrefs）。
  - **随后每 10 秒一轮、共 60 轮（10 分钟）：每轮 `ModSync.Apply("re-apply")` + `SelfCheck`**。
- `ModSync.Apply(tag)`：每次先 `ModBootstrap.ApplyChanges()`；返回 List 非空则 `InvalidateTableCache()` + `ModBootstrap.OnGameLoaded()` + `ForceReloadTables(硬编码3表)` + 再 `ApplyChanges()`。
- **性能头号嫌疑（S1）**：`local`（原 com.kimi.modmanager）包的 `menu_patch` 补丁目标是 `tbmainmenubutton`，该表 `ModTableTiers.IsHot=False`。由 v3 报告 §2.3 的反汇编，`ApplyChanges` 只要 ReenterOnly 返回非空就跳过热重建 —— 所以 **menu_patch 启用期间，每 10 秒一轮：清 241 条表字节缓存 + OnGameLoaded + 强制重载 3 张表 + 额外一次 ApplyChanges**。这是周期性的全量配置表重建。
- **性能二号嫌疑（S2）**：`_show=true` 时 `OnGUI` 每个事件（每帧 ≥2 次）都执行 `PackageSnapshot()`（IL2CPP 枚举）+ 逐 unit `IsEntryEnabled`（逐次跨 interop 边界）+ 字符串拼接。
- `ForceReloadTables` 的表名硬编码 `tbnpcbasecfg/tbnpcaipersona/tbmainmenubutton`（v3 §7.3 遗留）。
- `MarkerText="KIMI"`，环境变量 `KIMI_REV_TEST`，GUI 窗口标题 `"KIMI Mod Manager"`。

## P1. 性能下降调查与修复

### P1.0 测量方法（先立规矩，再谈结论）

要求报告给出**量化对照表**，场景至少：

| 场景 | 注入 | 插件 | 说明 |
|---|---|---|---|
| A 基线 | 无（直接启动 WorldApart.exe） | 无 | 启动耗时 + 同场景主观基准 |
| B 仅注入 | probe6 链 + BepInEx，**插件不装** | 无 | 隔离注入器/be.788 成本 |
| C 现状 | 全装 | 现版（10s 轮询 + 窗口常显） | 复现用户抱怨 |
| D 修复后 | 全装 | 修复版 | 验证修复 |

帧率测量：给插件加一个**轻量帧采样器**（`Time.unscaledDeltaTime` 累积，每 30s 输出 avg / p95 帧时间到日志，采样器本身每帧只做一次加法，开销可忽略）。场景 A/B 无插件，用外部对照：启动耗时（日志时间戳）+ 任务管理器/性能计数器记录稳态 CPU、内存、GPU 占用即可，不强制帧率。同场景同存档（用委托方测试档，河望镇客栈大堂），静置 3 分钟以上取稳态。

### P1.1 嫌疑人清单（按优先级，逐条 A/B 排除）

- **S1（头号）**：`Update()` 每 10s `ModSync.Apply` ×60 轮。menu_patch 启用 ⇒ `ReenterOnly` 恒非空 ⇒ 每 10s 全量：清 241 条缓存 + OnGameLoaded + ForceReloadTables(3 表) + 二次 ApplyChanges。**验证实验**：设 `MOD_PERF_SKIP_REAPPLY=1` 跳过 10s 轮询（其余不动），对比场景 C。预期 D 与 C 的差距主要由此解释。
- **S2（二号）**：`_show=true` 默认常显，OnGUI 每帧跨 interop 枚举包/查启用态。**验证实验**：默认隐藏（`_show=false`）对比。
- **S3**：probe6 `PreloadThread` TIME_CRITICAL + 启动期 `Sleep(1)` 自旋。只影响启动与装载期。**验证实验**：对比场景 A/B 启动到主菜单耗时；若差 >2s，把优先级降回 NORMAL（预载完成后）再测。
- **S4**：每 10s SelfCheck 读表 + 2 行日志。随 S1 一并消失，不单独实验。
- **S5**：LogOutput 写入量。对比各场景日志体积。

### P1.2 修复要求（调查证实后实施）

1. **删掉周期性 re-apply**：初始扫描 + Apply 之后，`Update` 不再定时调 `ModSync.Apply`。变更触发改为：用户 toggle / 游戏自身调 OnGameLoaded（Harmony postfix 已覆盖）/ 手动 F10 "Re-scan"。`SelfCheck` 改为按需（toggle 后 3s 做一次即可）+ 保留 `MOD_REV_TEST` 自测路径。
2. **F10 窗口默认隐藏**；窗口打开时包列表快照 1Hz 刷新，不要每帧 `PackageSnapshot()`。
3. S3 若实测有差：预载完成后 `SetThreadPriority` 降回 `THREAD_PRIORITY_NORMAL`。
4. **顺手清 v3 §7.3 遗留**：`ForceReloadTables` 表名去硬编码——从 `ModConfigOverlay.PatchedTableNames`（IEnumerable 代理）手动枚举取表名；取不到再回退硬编码清单并在日志注明。
5. **menu_patch 退役**：P2 落地后主菜单按钮补丁不再需要。本计划直接删除 `local.modmanager` 包的 `menu_patch` unit（`<M>` 与 `mod_template` 同步），`tbmainmenubutton` 从硬编码回退清单中也移除。`local.modmanager` 包骨架保留作将来模板。这同时让 S1 的周期性重建失去存在条件。
6. 修复版与现版在同场景的对照数据写入报告（avg/p95 帧时间、启动耗时、CPU/内存）。

### P1 验收标准

- 报告含量化对照表（A–D），修复后场景 D 的稳态 p95 帧时间与场景 B（仅注入）偏差 ≤5%（或给出无法达标的证据与下一步）。
- 日志无 Error/FATAL；10 分钟稳态运行无周期性卡顿的量化证据（帧时间曲线无 10s 周期尖峰）。
- 开关 toggle 双向可逆回归通过（沿用 v3 REV 流程，标记判据换 `【MOD生效·本地】`）。

## P2. MOD 管理器接入游戏设置界面

### P2.1 侦察（不动手改，先出结构结论）

1. 在 `KIMI\il2cpp_out\dump.cs` 检索 Settings/Option/Config 相关类（重点 `Game.dll`、`A1.UPF.BuiltinComponents.dll`、`A1GUI.dll`）：设置页的 View/ViewModel 类名、设置项集合类型（Loxodon ObservableCollection?）、设置页如何被主菜单打开（按钮命令绑定链）。
2. 用 `KIMI\tools\il2dis.py` 反汇编设置页构建函数：确认"往设置页加一项"的最小钩点（集合 getter / VM 构造函数 / 条目工厂）。
3. 顺带确认设置页 UI 的渲染路径（UPF 可视化树），评估注入一个完整自定义页 vs 复用现有列表加条目的成本。
4. 侦察结论写进报告 §P2-recon（类名、RVA、推荐钩点），**钩点方案超过一个时给对比**。

### P2.2 实现（在 P0 改名后的 `LocalModManager` 上做）

- 复用现有内核：`PackageSnapshot` / `Apply` / `ModSync` / `SetAllEntries` 抽成与 UI 无关的静态核心，IMGUI 窗口与设置页入口都调它。
- 方案优先序：
  - **方案一（首选）**：Harmony postfix 钩设置项集合的构建点，追加 "MOD 管理" 条目，点击打开管理面板。面板 UI 若 UPF 自定义页成本可控就做 UPF 页；成本过高则该入口直接唤起重排版的 IMGUI 窗口（默认隐藏、1Hz 快照，见 P1.2-2）。
  - **方案二（兜底）**：若设置页结构无法安全注入，退而求其次在**主菜单**注入（已有 `tbmainmenubutton` 补丁先例，但注意它是 Reenter 级表，v3 §7.4 警告过热重建路径不一定能让按钮出现——所以这只是兜底，且需单独验证重进路径）。
- 管理面板内容最低要求：按包分组列出 unit，点击 toggle 即时生效（`Apply` → `ModSync`），显示当前生效状态；F10 调试窗口保留。

### P2 验收标准

1. 委托方截图：游戏主界面 → 设置 → 可见 "MOD 管理" 入口。
2. 从该入口进入管理面板，关闭 `basecfg_patch` 后档案页标记消失、再开启后恢复（`SELFCHECK` 日志 + 委托方截图各一）。
3. 全流程不依赖 F10；F10 窗口仍可用作调试。
4. 若走方案二兜底，报告必须说明方案一失败的具体证据（类名/反汇编结论），不得无理由降级。

## P3. 全局剧情编辑器（设计文档，本阶段不写代码）

产出 `KIMI\剧情编辑器设计.md`，至少覆盖以下章节：

1. **目标与范围**：全局剧情脉络浏览（章节/节点/分支图）、人物总览（基础档案 + AI 人格）、视频资源总览及其与剧情节点的关联；支持增/删/改人物、剧情文字、剧情视频引用；成果一键导出为标准 Mod 包（走 v3 定型的补丁管线，**只生成补丁包、永不改原始 bundle**，保证可逆、可走游戏原生 Mod 管线验收）。
2. **数据清单与 M1 侦察项**：配置 bundle 剥头 + UnityPy 读表流程（已有）；`.json` sidecar 作为 schema 参照；**待枚举**：完整表目录（从 bundle 索引）、剧情章节/对白表名、视频引用字段（哪张表哪个字段持有 A1ResourceSystem 资源地址）、视频资产本体格式与加载方式（AVPro/A1ResourceSystem）。M1 侦察是设计文档的第一里程碑，列出具体待查文件与验证方法。
3. **架构选型**：对比 (a) 游戏内 BepInEx 覆盖层（进程内实时数据、UI 受 UPF 限制）与 (b) 外部桌面编辑器（离线 UnityPy 解析、可做富交互与图谱可视化、改完导出补丁包再进游戏验证）。**推荐 (b)**，论证取舍；(a) 可作为远期只读查看器。
4. **数据模型**：实体（NPC、AI人格、剧情章节、对白节点、视频资源）与关系（人物↔人格、章节↔节点↔对白、节点↔视频）的 ER 描述；与 `tbnpcbasecfg`/`tbnpcaipersona` 等现有表行的映射规则；`keyFields` 的确定方式（每表从 `.json` schema 推导）。
5. **写路径与导出**：编辑器内部表示 →  diff → `{"keyFields","upsert","remove"}` 补丁 JSON → 打包 `local.*` 目录结构（mod.json schemaVersion=5）→ 游戏内启用验证的闭环；删除语义的表示（`remove` 数组 + 引用完整性检查）。
6. **校验与防错**：schema 校验、引用完整性（npcId 存在性、章节顺序、视频地址可达）、导出前模拟应用（对 dump 出的表做内存 diff 预览）。
7. **UI 规划**：剧情脉络图（节点-边）、人物列表、视频库、属性编辑面板、导出向导；草图用文字+ASCII 描述即可。
8. **里程碑**：M1 数据侦察（表目录+视频引用链）→ M2 只读查看器（表+图谱）→ M3 编辑器（增删改+导出+游戏内验证）→ M4 打磨（撤销、diff 预览、批量导出）。每里程碑给验收标准。
