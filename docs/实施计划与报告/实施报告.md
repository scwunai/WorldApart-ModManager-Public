### 三条推翻交接文档原判断的实测结论

1. **交接文档 4.1 的"卡点"是误判。探针一直在成功加载。**
   `probe.c` 用自身模块路径推导写日志目录，实际写到 `KIMI\injector\kimi_probe.txt`，不是文档与 `probe.c` 注释里写的 `<G>\kimi_probe.txt`。该文件早已存在：

   ```
   KIMI\injector\kimi_probe.txt
   PROBE: DLL_PROCESS_ATTACH
   PROBE: doorstop load FAILED err=126
   PROBE: DLL_PROCESS_ATTACH
   PROBE: doorstop load FAILED err=126
   PROBE: DLL_PROCESS_ATTACH
   PROBE: doorstop load FAILED err=126
   ```

   原始基线里 `KIMI\injector\kimi_inject.log`（改造前的 wastart）只写到
   `INJECT: remote thread created, waiting` 就结束——旧版代码在**成功路径上不打任何日志**，
   所以看起来像卡死。把注入段改造成手动轮询后，同一个探针目标立刻打出
   `OK: remote thread returned after 1000ms, exit code=0xd94f0000`（`0xd94f0000` 正是
   probe2.dll 在该进程内的加载基址）。即远程线程正常返回、`LoadLibraryW` 成功。
   H1/H2/H3/H4 四条假设**全部不成立**。

2. **真正的根因：gpShell 把 exe / UnityPlayer.dll / GameAssembly.dll 的导入表整体剥离成单个 `gpShell.dll!gShell` 存根。**
   实测（`probe2`，进程内 dump 内存中的 IAT，原文见 `KIMI\probe_dump.txt`）：

   ```
   [main-exe] ... IAT[0] gpShell.dll funcs=1          has GetProcAddress in IAT: NO
   [UnityPlayer] ... IAT[0] gpShell.dll funcs=1       has GetProcAddress in IAT: NO
   [GameAssembly] ... IAT[0] gpShell.dll funcs=1      has GetProcAddress in IAT: NO
   [gpShell] ... IAT[0] KERNEL32.dll funcs=140   <<< GetProcAddress HERE
   ```

   doorstop 4.3 的激活逻辑是 `inject()` → `iat_hook(GetModuleHandle("UnityPlayer"), "kernel32.dll", GetProcAddress, detour)`。UnityPlayer.dll 的导入描述符里根本没有 `kernel32.dll`（只有 `gpShell.dll`），所以 `iat_hook` 返回 FALSE，doorstop 打印 "Failed to install IAT hook!" 后**静默放弃**——而它的 `LOG()` 宏在未开启 VERBOSE 编译时是空操作（已核对 `kimi_door.dll` 里不存在 `doorstop_%lx.log` 等日志字符串）。这就是"代理在却毫无输出"的全部原因。

3. **不能碰 gpShell。** 给 gpShell.dll 的 `KERNEL32!GetProcAddress` IAT 打 detour 后，Unity 直接弹 `Fatal error: Failed to load il2cpp`（该字符串来自 `UnityPlayer.dll`，偏移 26782520），进程随后以托管异常 `0xe0434352` 退出。gpShell 会检测自身被篡改。最终方案完全不修改 gpShell 的任何字节。

## 2. 实验矩阵

### E1 —— helper 死活与远程线程超时路径

**假设**：`WaitForSingleObject` 行为异常 / helper 已死。

**改动**：`KIMI\injector\wastart.c` 重写注入段为手动轮询（`WaitForSingleObject(th,0)` + `GetExitCodeThread`，每 1s 记一次），并在每条路径写明确的 OK/FAIL 行。

**观察**（`KIMI\injector\kimi_inject.log`，probe2 基线）：

```
INJECT: remote thread created, polling
OK: remote thread returned after 1000ms, exit code=0xd94f0000 (3645833216)
DONE: injection call completed, LoadLibraryW result=0xd94f0000
```

返回值 `0xd94f0000` 正是 probe2.dll 在该进程内的加载基址，即 `LoadLibraryW` 返回值。

**结论**：helper 活着，远程线程 1s 内正常返回，`LoadLibraryW` 成功。E1 假设不成立。顺带修掉了"成功也不打日志"的可观测性缺陷。

---

### E2 —— 无操作远程线程对照（判别 H4）

**跳过的实验，原因**：H4（远程线程机制被劫持）在 E1 已被直接证伪——远程线程既正常创建也正常返回，且探针 DllMain 真实执行（标记文件有内容）。再做 `GetTickCount` 对照没有信息增量。
（`wastart.c` 仍保留了 `inject.ini` 的 `entry_tick=1` 开关，需要时可随时复跑。）

---

### E3 —— 注入时机扫描（判别 H2/H3）

**改动**：`inject.ini` 增加 `delay_ms` / `target_mode`；`FindTarget(mode=2)` 改为"任意非壳进程的 WorldApart* 子进程"（不要求 UnityPlayer 已加载），轮询间隔 25ms→5ms。

**观察**：

- 注入点从"UnityPlayer 已加载"（约进程龄 250ms）提前到"进程刚创建"（约 46ms）后，游戏行为完全一致：
  - `KIMI\run_E5g.log` 与 `KIMI\run_E5h.log` 的运行期间进程列表稳定存在，无错误对话框。
- 但每次运行 GameAssembly.dll 出现的时刻不稳定：31ms（`KIMI\probe_dump.txt`）到 125ms（另一次运行）。

**结论**：不存在"启动窗口期检测"（H3 不成立）；注入时机越早越好，但**"何时 GameAssembly 加载"不可预测**，靠轮询撞窗口不可靠（后续用"自预加载"彻底解决，见 E5）。

---

### E4 —— 注入目标对照

**观察**：`target_mode=1`（壳进程）与 `target_mode=2`（Unity 子进程）都能成功 `LoadLibraryW`。
**结论**：目标进程不是瓶颈。壳进程里加载的 DLL 对 Unity 子进程无效（DLL 不跨进程继承），因此必须打 Unity 子进程。

### E5 —— 打通链路（本案核心）

分五步，每步都以实测否掉一条路线。

#### E5.1 在 gpShell 的 KERNEL32 IAT 上钩 GetProcAddress（`probe3.c` / `KIMI\run_E5c.log`）

**假设**：UnityPlayer 通过 gpShell 解析 il2cpp_init，钩住 gpShell 的 GetProcAddress 即可截获。

**改动**：`PatchIatEntry(gpShell, "KERNEL32.dll", real_GPA, det_GPA)`。

**观察**（`KIMI\probe_dump.txt`）：

```
gpShell=00007FFB61DF0000
  patch KERNEL32.dll IAT[0] slot 13: 00007FFC0E7A2190 -> 00007FFBDA082020
PATCH results: GetProcAddress=1 LoadLibraryW=1 LoadLibraryExW=1
...
GPA(KERNEL32.DLL, TlsAlloc)
...（共 169 次，全部在注入后 30ms 内）
WATCH: t=104578ms gpa_calls=169 il2cpp_hits=0 wrapper=0
```

**结论**：钩子生效，共截获 169 次解析，但**从头到尾没有一次 `il2cpp_init`**。同时游戏弹 `Fatal error: Failed to load il2cpp`（UnityPlayer.dll 内字符串），进程以 `0xe0434352`（托管异常）退出——**gpShell 检测到自身 IAT 被改**。该路线废弃，且**确立了"绝不修改 gpShell"这条硬约束**。

#### E5.2 改写 GameAssembly 导出表（EAT）里的 il2cpp_init（`probe4.c` / `KIMI\run_E5d.log`）

**假设**：解析方走 EAT，只要在解析前把 EAT 项指向我们的桩即可。

**改动**：`PatchEat(GameAssembly, "il2cpp_init", stub)`，桩为该模块 ±2GB 内的 `mov rax,imm64; jmp rax`（12 字节）。

**观察**（先踩两次坑）：
1. `MEM_EXTENDED_PARAMETER.Type` 误用 2（`MemExtendedParameterNumaNode`），应为 1；`VirtualAlloc2` 全部失败。
2. 修正后仍失败——GameAssembly 上方 2GB 地址空间已被占满：

   ```
   EAT: GameAssembly=00007FFA3D0F0000 stub=0000000000000000 (delta=-140712742944768)
   EAT FAIL: no executable memory within +-2 GB of GameAssembly
   ```

   因为 EAT 存的是 32 位**无符号** RVA，桩必须在模块上方，而下方的分配无法表示。
3. 改用 GameAssembly 自身 `.text`/`il2cpp` 段内的填充字节作为 code cave（`0xCC`/`0x00` 连续 32 字节），成功：

   ```
   CAVE: found 32 x0x00 at 00007FFA4232CDD4 (rva 0x523cdd4, section il2cpp)
   EAT: il2cpp_init EAT[ord 153] 0x571c30 -> rva 0x523cdd4 (stub 00007FFA4232CDD4)
   EAT: real il2cpp_init = 00007FFA3D661C30
   ```

**观察（结果）**：游戏正常运行 119s 无异常，但

```
WATCH: t=119422ms hooked=1 wrapper=0 boot=0 done=0
```

**wrapper 始终为 0——游戏从未按名字解析 `il2cpp_init`**（既不走 EAT，也不走 gpShell 的 GetProcAddress）。EAT 路线废弃。

#### E5.3 `LdrRegisterDllNotification` 捕获 GameAssembly 加载（`probe5.c` / `KIMI\run_E5f.log`）

**假设**：在 DLL 加载通知里第一时间给 il2cpp_init 打内联钩子，可做到与调用者的竞态为零。

**改动**：`InitThread` 里 `LdrRegisterDllNotification(0, DllNotify, NULL, &cookie)`，并给回调加计数日志。

**观察**：

```
===== PROBE5 attach pid=44864 tid=43232 mode=full fallback=0ms notify=1 =====
LdrRegisterDllNotification=00007FFC10069310 status=0x00000000 cookie=0000000000663570
GameAssembly not loaded yet (good)
（此后无任何行；进程 5s 内消失）
```

WER：`WorldApart_kimi.exe` APPCRASH，`0xc0000005`，故障模块 `UnityPlayer.dll`。

**结论**：**注册 DLL 加载通知会被 gpShell 判定为可疑并导致崩溃**，而且回调一次都没被调用。该路线废弃（与 §0 第 3 条同源：gpShell 主动反注入）。

#### E5.4 自预加载 GameAssembly + 内联钩 il2cpp_init（`probe6.c`，成功）

**思路**：既然解析路径不可钩、通知被检测、EAT 无效，就**绕开"谁在什么时候解析"这个问题**：由我们自己在 UnityPlayer 之前 `LoadLibraryW(GameAssembly.dll)`，加载返回后立刻改掉 `il2cpp_init` 函数体首 16 字节。这样与调用者零竞态——UnityPlayer 之后无论用 EAT、用缓存指针还是直接调用，拿到的都是已经被改过的函数体。

**改动**（`KIMI\injector\probe6.c`）：
1. 注入后立刻起 `PreloadThread`（TIME_CRITICAL 优先级）载入 `<G>\GameAssembly.dll`；
2. `HookIl2cppInit()`：存前 16 字节 → 写入 `mov rax,&our_il2cpp_init; jmp rax` + 4 个 `0xCC`；
3. `our_il2cpp_init()`：临界区内**还原原始 16 字节 → 调用原始 il2cpp_init → 重新装钩**，然后执行 doorstop 的 CoreCLR bootstrap（见 §2 的 E7）；
4. 轮询作为兜底（1ms，winmm `timeBeginPeriod(1)`）。

**观察**（`KIMI\probe_dump.txt`，本次成功运行）：

```
PRELOAD: LoadLibraryW(<G>\GameAssembly.dll)
PRELOAD: -> 00007FFA05520000 err=0 after 94ms
HOOK: GameAssembly=00007FFA05520000 il2cpp_init=00007FFA39401C30
HOOK: prologue 40 53 48 83 ec 20 48 8b d9 48 8d 15 cf b3 15 06
HOOK: il2cpp_init patched (16 bytes stolen)
WRAPPER: il2cpp_init("IL2CPP Root Domain") entered
WRAPPER: original il2cpp_init returned 1
WRAPPER: hook re-armed
BOOTSTRAP: enter
...
BOOTSTRAP: done
WRAPPER: returning 1
```

注意：预加载路径最初有个手写路径拼接的转义 bug（`L"%s\GameAssembly.dll"`，反斜杠被吃掉 → 打出 `A1GameAssembly.dll`，err=126），修成 `\\` 后 `PRELOAD` 才真正生效。**修复前只能靠轮询碰运气**——同一份 probe6 在 `KIMI\run_E7c.log` 那次运行里 `GameAssembly at ... (t=125ms)` 已经太晚，`wrapper=0`，游戏随后死亡；修好后（`PRELOAD ... after 94ms`）每次都稳定命中。

**结论**：链路打通。E5.4 为最终方案。

### E6 —— 分析 gpShell 的加载路径干预

**跳过（部分完成），原因**：E5.4 已成功，无需继续逆向 gpShell。但过程中已经实测到 gpShell 的三条防护行为，记录如下（可供将来参考）：

|---|---|

## 3. 卡点结论与证据链

**最终定位**：注入链路本身从头就是通的；卡点是**doorstop 4.3 的激活机制（IAT 钩 UnityPlayer 的 kernel32!GetProcAddress）与本作的 gpShell 导入表剥离方案不兼容**，而 doorstop 在失败时因编译期关闭日志而完全静默。

证据链（自下而上）：

1. 内存态 IAT 实测：`UnityPlayer.dll` / `GameAssembly.dll` / 主 exe 的导入描述符只有一个 `gpShell.dll`（1 个函数 `gShell`），磁盘 PE 亦如此（`KIMI\tools\peinfo.py` 输出）。→ doorstop 的 `iat_hook(...,"kernel32.dll",...)` 必然匹配不到。
2. `probe3`：钩住 gpShell 的 `KERNEL32!GetProcAddress` 后，169 次解析全部可见，**`il2cpp_init` 一次都没出现**。→ 本作不走"按名字解析 il2cpp_init"。
3. `probe4`：把 GameAssembly 的 EAT 里 `il2cpp_init` 改写成功、游戏 119s 稳定，但 wrapper 从未触发。→ 也不走 EAT。
4. `probe5`：`LdrRegisterDllNotification` 注册成功但回调零调用、进程崩溃。→ gpShell 主动反注入。
5. `probe6`：自行预加载 GameAssembly + 内联改函数体 → wrapper 立即触发，链路贯通。

## 6. 遗留风险与下一步

1. **游戏内标记待人工确认（最高优先）。** 请进游戏 → 打开苏倾盏（npcId=100000）档案页，看 `propPlot` 是否变成【KIMI·MOD生效】…。若仍是原文，按 §5.4 的 (a)/(b) 继续排查：最可能是需要在游戏进入存档/世界后（`ModBootstrap.OnGameLoaded` 之后）再调一次 `ApplyChanges()`——插件已每 10s 重试 12 轮，如果确认是这个原因，把重试窗口拉长到"进入游戏后每分钟一次"即可。

4. **BepInEx 版本被替换。** be.697 → be.788。若本作日后更新到更新的 Unity，仍可能再次撞上元数据版本，届时继续取最新 be 构建即可；原 be.697 核心在 `KIMI\backup_core_be697\`。
